# API Documentation

Interactive docs: `http://localhost:8000/docs` (OpenAPI generated by FastAPI).

## Principles

Typed requests/responses, bearer-token authentication, server-side RBAC and tenant scoping on every route,
consistent error envelope, `X-Correlation-ID` on every response and audit event.

## Envelope

```json
{"data": {...}, "error": null}
{"data": null, "error": {"code": "INVALID_REQUEST", "message": "Request validation failed", "correlation_id": "uuid"}}
```

Error codes: `INVALID_REQUEST` 400, `UNSUPPORTED_FILE` 400, `UNAUTHENTICATED` 401, `FORBIDDEN` 403,
`NOT_FOUND` 404 (also returned for resources in another tenant), `INVALID_TRANSITION` / `INVALID_STATE` /
`NOT_APPROVED` / `CLOSE_BLOCKED` / `EVIDENCE_INTEGRITY` / `WORKFLOW_ACTIVE` / `GRAPH_DISABLED` 409,
`FILE_TOO_LARGE` 413, `RATE_LIMITED` 429, `INTERNAL_ERROR` 500, `GRAPH_UNAVAILABLE` 503.

## Notifications

Workflow events create in-app notifications (review required, assignment, failed verification, overdue escalation).
Each one is also queued for email in `notification_deliveries` in the same transaction. The `deliver-notifications`
job (`python -m app.jobs escalate-overdue deliver-notifications`) sends due rows with the adapter in
`SITEGUARD_NOTIFICATION_EMAIL_ADAPTER`: `disabled` (default; rows become `SKIPPED`), `log` (records that a message
would be sent, without address or content) or `smtp` (STARTTLS; refused in local and test). A failed send is retried
after 1, 5, 25 ... minutes up to `SITEGUARD_NOTIFICATION_MAX_ATTEMPTS`, then becomes `FAILED` until an administrator
retries it. Delivery never changes workflow state. Emails carry the notification text and a link to the incident in
the web app.
